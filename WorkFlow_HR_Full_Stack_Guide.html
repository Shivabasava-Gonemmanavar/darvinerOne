WorkFlow HR
Full-Stack Architecture

A code-based walkthrough of how the browser, JavaScript modules, Express API, MySQL database, sessions, and uploaded files fit together.

What you will understand

How a click in the UI becomes an HTTP request, how the API authenticates and authorizes it, how prepared SQL reads or writes MySQL, how the response updates the page, and where persistent data is stored.

This guide describes the project in this repository. It is not a generic HR-system design. Secrets and real passwords are intentionally excluded.

1. The application in one picture

WorkFlow HR is a same-origin web application: Express serves the browser files and its API from the same Node.js process. The browser does not connect to MySQL. Only the backend has database credentials.

PERSON │ uses ▼ Browser: index.html + styles.css + ES modules in src/ │ fetch('/api/v1/...') + session cookie ▼ Express server: middleware → authentication → role/scope checks → route handler │ mysql2 prepared query / transaction ▼ MySQL: workflow_hr tables Related persistence: express-session ── session ID cookie ── MySQLSessionStore ── web_sessions Uploaded documents ── server/uploads/ (private local filesystem in this version)

The browser keeps a temporary in-memory copy of the records currently displayed. MySQL is the durable source of truth. Refreshing the page reloads records from the API; it does not restore them from localStorage.

3. Frontend: what happens in the browser

3.1 Entry and modules

index.html loads styles.css and starts src/app.js as a native JavaScript module. The main module imports controllers, services, shared state, and HTML helpers. The browser renders pages by updating DOM elements; it is not a server-rendered React application.

3.2 Browser startup and login

  1. The browser loads HTML, CSS, and JavaScript.
  2. src/app.js calls GET /api/v1/auth/me.
  3. If the server recognizes the session cookie, the UI loads GET /api/v1/bootstrap, fills in-memory state, and shows the app shell.
  4. If there is no valid session, the login screen remains visible.
  5. Submitting the login form calls POST /api/v1/auth/login. On success, bootstrap data is fetched and the UI renders navigation for the user’s role.

3.3 Client state is a cache, not the database

state.data contains arrays such as employees, leaves, holidays, attendance, payslips, and tickets. A successful write usually calls refreshBootstrap() and re-renders. Closing or refreshing the browser loses this in-memory copy, but not committed MySQL data. Compatibility functions named saveData, saveUsers, and saveSession intentionally do nothing.

4. API and backend: how requests are handled

4.1 One normal request

Button/form event → controller calls a domain service → apiClient.fetch('/api/v1/...', { credentials: 'include' }) → Express parses JSON or multipart form data → session middleware reads workflow.sid and loads web_sessions row → requireAuth reloads active user + employee from MySQL → attachDepartment loads the employee's department for scope checks → route validates input and checks role / record scope → mysql2 executes prepared SQL (or a transaction) → JSON response / file stream → service refreshes browser state and controller re-renders

4.2 Middleware order and common behavior

  • Express disables the X-Powered-By header, applies Helmet headers, then parses JSON (up to 15 MB) and URL-encoded bodies (up to 2 MB).
  • Session middleware is installed before application routes. The session cookie is named workflow.sid, HttpOnly, SameSite=Lax, expires after 8 hours, and is Secure in production.
  • asyncRoute forwards rejected async handlers to common error middleware. API errors generally return JSON like {"error":{"message":"..."}}.
  • fail() creates consistent API errors. Unmatched versioned API routes return 404.
  • /api/health runs SELECT 1. It confirms the server can reach MySQL, but does not verify every schema table or complete business workflow.

5. Authentication, sessions, roles, and security

Password and session lifecycle

  1. The seed script or Admin employee-creation route hashes a password using bcryptjs with cost factor 12, then writes only the hash into users.password_hash.
  2. Login looks up a user by normalized email, requires both active user and active employee, then uses bcrypt.compare.
  3. After success, Express regenerates the session ID to reduce session-fixation risk and stores the user’s numeric users.id as req.session.userId.
  4. The browser receives only an HttpOnly session cookie. The session body remains server-side in web_sessions.
  5. On protected API requests the server reloads the user and employee; a disabled user or inactive employee is rejected even if an old cookie exists.
  6. Logout destroys the database session and clears the cookie.

Roles and scope

RoleTypical visibility/actionsWhere enforced
EmployeeOwn employee profile, attendance, leave, tickets, and payslips.Backend SQL filters by current employee ID; UI also hides management navigation.
ManagerDepartment-level team records and approvals; cannot manage the whole company.Backend checks department ID on reads and protected writes.
AdminCompany-wide management, accounts, holidays, payslip uploads and deletes.Backend role middleware and per-route rules.
Important: Hiding a button in JavaScript is not security. The API is the security boundary. This project does server-side role and scope checks on protected routes.

Other protections include parameterized SQL, Zod request validation, a login rate limit, upload type/size checks, a private uploads directory, production session-secret length enforcement, and Helmet headers. The Content Security Policy is disabled in code, so it is not one of the protections currently provided.

6. MySQL data model and relationships

The application uses raw SQL with mysql2, not an ORM. IDs are generally BIGINT UNSIGNED. The API converts database rows into smaller browser-facing objects so internal columns such as password hashes are not returned.

Two different employee identifiers

MySQL uses numeric employees.id for foreign keys. The UI/API commonly displays the human-readable employee_code such as EMP001. Keep them distinct: the API converts DB IDs into employee codes for employee lists, while attendance/payslip rows have their own numeric record IDs.

7. The main business flows

Employee creation

An Admin submits an employee form. The API validates fields, begins a MySQL transaction, creates or reuses the department, inserts the employee, hashes the initial password, inserts the linked login user, and commits. Duplicate employee code or email returns a conflict response. A failed transaction rolls back both records.

Attendance

The server computes the current calendar date in Asia/Kolkata. It marks a check-in Late after 09:45 India local time; otherwise Present. The persisted event timestamp is UTC. A unique employee/date key prevents a second check-in. Check-out updates only an existing open row for today. API view helpers convert dates and times for the browser.

Leave application and approval

  1. The browser can preview working days using weekdays and the currently loaded holiday list.
  2. The server independently validates the leave type, dates, reason, and document. It queries holidays in the requested range and recalculates the weekday count; the client is not trusted for the final count.
  3. The server compares requested days with the current leave balance. Paid days and loss-of-pay (LOP) days are stored separately. A Paid Leave request with insufficient balance is rejected.
  4. Sick leave longer than three working days requires a PDF/PNG/JPEG. The server checks the file signature as well as the data URL type and writes the document to the private uploads folder.
  5. A Manager/Admin approval starts a transaction, locks the leave row with FOR UPDATE, checks Pending status and department scope, deducts paid days only on approval, updates reviewer/status, then commits.

Holidays, tickets, reports, payslips

  • Holidays: Admin creates a unique date; holidays affect leave-day calculations.
  • Tickets: an employee creates a ticket; Manager/Admin can change its status, with managers limited to their department.
  • Attendance reports: server returns month-filtered rows and role scope; browser builds a downloadable Excel-compatible HTML file with an .xls extension.
  • Leave reports: built in the browser from bootstrap data. Manager scope is assembled client-side using employee names/departments in the loaded data.
  • Payslips: Admin uploads a PDF; Multer stores it in server/uploads/payslips, the server checks the PDF signature, and MySQL stores its metadata/path. Downloads check that a non-Admin owns the payslip before sending it. The uploads directory must never be exposed as public static content.

9. Configuration and important boundaries

  • PORT: server listening port; default 3000.
  • APP_ORIGIN: documented local/production origin value; inspect route code before assuming every environment variable is actively used.
  • SESSION_SECRET: signs session cookies. Production requires at least 32 characters.
  • DB_HOST, DB_PORT, DB_NAME, DB_USER, DB_PASSWORD: runtime MySQL connection.
  • DB_ADMIN_USER, DB_ADMIN_PASSWORD: elevated credentials used by migration and must be protected.
  • UPLOAD_DIR, MAX_UPLOAD_MB: local private storage location and payslip upload limit.
  • .env and uploaded files are ignored by Git. Never commit production secrets, real payroll files, or local DB credentials.
Local versus live: Local MySQL at 127.0.0.1 is only reachable on the local computer. A Vercel deployment cannot use that address to reach your Windows machine. A live deployment also needs a network-accessible production database, production environment variables, and durable private file storage; the current local upload folder is not production-grade durable storage.

12. Learning path: trace one feature end to end

  1. Pick a button in a view/controller, for example check-in in src/controllers/dashboardController.js.
  2. Follow the service it calls, such as src/services/attendanceService.js.
  3. Find the API path passed to api() and note the HTTP method/body.
  4. Find the matching Express route in server/src/index.js.
  5. Trace its middleware: session, authentication, department attachment, and role checks.
  6. Read the SQL statement and identify its table, key, and transaction behavior.
  7. Find the JSON response shape; compare it with the frontend state/view fields.
  8. Check the schema constraint that protects the data (for example, the unique employee/date attendance key).
Best mental model: UI code improves usability; API code owns validation, identity, permissions, and business rules; MySQL constraints protect persisted relationships and uniqueness. Follow the request from the button to the SQL and back to the rendered state.
